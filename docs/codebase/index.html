Current status

The graphics API supports one front-facing render path and two graphics backends. The ECS provides generation-checked entities, sparse-set component storage, views, and typed queries.

Use ECS::World for entity and component storage. A replacement ECS-to-render adapter is not implemented yet.

The API supports one swapchain color target, one internal depth target, one texture and sampler per draw, mesh draws, sprite draws, and ImGui. It does not yet support compute work, instanced draws, indirect draws, or shadow passes.

Render architecture

Each layer has one responsibility. Backend types stay behind the graphics device interface.

user code→ RenderWorld→ Renderer→ RenderResourceManager→ IGraphicsDevice→ OpenGL or Vulkan
RenderWorld
Owns persistent render instances and one-frame submissions.
Renderer
Collects visible items and records graphics commands.
RenderResourceManager
Converts asset handles into cached GPU resources.
IGraphicsDevice
Owns GPU resources, frame submission, and presentation.

Design rules

  • Use one public render submission API.
  • Keep component data independent from renderer storage.
  • Use typed handles. Do not expose native graphics objects.
  • Keep OpenGL and Vulkan behavior behind the same contract.
  • Add graphics features only when a front-facing requirement needs them.
  • Invalidate GPU resources outside an active frame.
